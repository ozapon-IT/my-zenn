## TL;DR

- GMOコインFX の `cancelOrders` も `closeOrder` も、**API の成功は「受付」**であって反映済みという意味ではありません。公式のレスポンス説明も「取消**受付**に成功した親注文IDと顧客注文ID」です(2026年8月時点で確認)
- 取消 POST の直後に `activeOrders` を GET したら**取消前の状態が返ってきました**。自分はこれを見て「取消が効いていない」と誤判定しかけました
- 反映の判定に使えたのは、建玉(`openPositions`)の **`orderedSize`(注文中数量)** でした。取消が反映されると `"100"` → `"0"` に落ちます
- 決済 OCO が有効注文の枠を押さえたまま満額の `closeOrder` を投げると、**ERR-423** の後半条件「総有効注文数量との合計が総建玉数量よりも大きい場合」に触れ得ます。対策として、取消と決済のあいだに `orderedSize == 0` まで短ポーリングを入れました
- ただし **ERR-423 自体は自分のスパイクでは観測していません**(取消が効いてしまい到達しなかった)。本記事は「公式の条件」「実測した反映ラグ」「予防としての実装」を分けて書きます
- 決済シーケンス全体の設計は [Kill Switch の冪等設計](https://zenn.dev/ozapon/articles/gmo-fx-kill-switch-idempotency) に書いています。本記事はその中の**取消反映待ち**だけを掘り下げた枝葉です

## 背景

GMOコインFX の API を使う自動売買システム(Python / AWS Lambda)で、全建玉を手仕舞いするシーケンスを実装しています。定時手仕舞いバッチと非常停止(Kill Switch)が共有する処理です。

このシーケンスは「**キャンセル・ファースト**」と呼んでいる順序規約で動きます。決済の前に必ず未約定注文を取り消す、という規約です。

- Step1: 新規注文(`settleType` が `OPEN`)のキャンセル
- Step2: 決済注文(`settleType` が `CLOSE`、実体は決済 OCO)のキャンセル
- Step3: 残った建玉を `closeOrder` で成行クローズ

Step3 は `closeOrder` の `settlePosition` 配列(最大10件)で建玉を指定します。FX API 側に `closeBulkOrder` は無いため、一括決済はこの形になります(2026年8月時点)。

問題にしたいのは、**Step2 と Step3 のあいだに何も待たなかった**ことです。

## 問題

実発注のスパイクで、1次注文が約定済みの IFD-OCO(2次注文＝決済 OCO が 2 件、同一の親注文ID を共有)に対して `cancelOrders` を投げました。レスポンスは成功です。

```json
// POST /private/v1/cancelOrders  {"rootOrderIds": [<親注文ID>]}
{"status": 0, "data": {"success": [{"rootOrderId": <親注文ID>}]}}
```

ところが、**直後に `activeOrders` を GET すると取消前の注文がそのまま返ってきました**。レスポンスの `responsetime` を見ると、GET の時刻が POST の時刻より前になっている、という事象まで観測しています。

このとき自分は「`cancelOrders` の呼び方が間違っていて取消が効いていないのでは」と疑いました。実際にはパラメータは正しく、しばらく後に確認したら取消は反映されていました。**誤判定しかけたのは、受付と反映を同じものとして扱っていた自分の判定ロジックのほう**です。

より怖いのは、この誤判定が読み取り側で止まらない場合です。取消が未反映のまま Step3 に進むと、決済 OCO が有効注文として枠を押さえたまま、建玉の満額を決済しようとすることになります。

## 原因

### 受付と反映は別

`cancelOrders` のレスポンス説明は、公式ドキュメントでも「取消**受付**に成功した親注文IDと顧客注文ID」です(2026年8月時点で確認)。`closeOrder` 側も同様で、成功レスポンスの `status` は `WAITING` を取り得ます。つまり**どちらも「受け付けた」までしか保証していません**。

反映がいつ完了するかは公開されていません。自分の実測は「POST 直後の GET には反映されていなかった」という一点で、遅延の長さそのものは測れていません。

### ERR-423 の後半条件

公式のエラーコード表には、ERR-423 について次の記載があります(原文・2026年8月時点で確認)。

> 決済注文において注文数量が(指定した建玉、もしくは指定銘柄の建玉の)総建玉数量よりも大きい場合、もしくは総有効注文数量との合計が総建玉数量よりも大きい場合に返ってきます。

後半の「総有効注文数量との合計が総建玉数量よりも大きい場合」が、今回**踏み得ると見ている**シナリオです。決済 OCO が生きたまま建玉の満額を `closeOrder` すると、有効注文数量＋決済数量が建玉数量を超えます。

同じ趣旨は ERR-200 の説明にも書かれています。こちらは対処まで明示されています(原文・2026年8月時点で確認)。

> すでに有効注文があり、注文数量が発注可能な数量を超えている場合に返ってきます。決済注文を行いたい場合は、注文数量を変更するか、有効注文を取消したうえで、再度注文をしてください。

公式が案内している「有効注文を取消したうえで、再度注文」がそのままキャンセル・ファーストの順序です。自分の設計はこの案内と同じ方向を向いていたわけですが、**「取消したうえで」が受付ではなく反映を指すこと**を実装に落とせていませんでした。

### ERR-189 との区別

数量超過には ERR-189 もあります。公式の説明は「決済注文において、決済可能保有数量を超えての数量の注文の場合に返ってきます」です(2026年8月時点で確認)。自分のスパイクでは、建玉数量より明らかに大きい `size` を送ったとき、実際に返ってきたのは ERR-423 ではなく **ERR-189**(`message_string` は `"Exceeds the order quantity."`)でした。

ここから、ERR-423 は後半条件(有効注文の枠)寄りではないか、と推測しています。ただし**これは推測です**。ERR-423 自体は、Step2 の取消が効いてしまったため当該スパイクでは観測できませんでした。

したがって本記事の主張は「ERR-423 をこう直した」ではなく、「公式の条件と実測した反映ラグから、**踏み得ると判断して予防した**」です。

### `activeOrders` の件数を即判定に使わない

反映を確認する指標として最初に思いつくのは `activeOrders` の件数ですが、上記のとおり取消直後の GET は取消前の状態を返し得ます。**件数 0 になったことを即座の完了条件にすると、遅延をそのまま誤判定として拾います**。

一方、建玉側の `orderedSize`(公式の説明は「注文中数量」、型は string)は、取消の反映にともなって `"100"` → `"0"` に落ちるのを実測できました。同じスパイクの範囲では、これが最も信頼できる指標でした。

## 解決策

Step2 と Step3 のあいだに、建玉の `orderedSize` が 0 になるまでの短ポーリングを挟みました。以下は実装からの抜粋です(ログ出力は省略)。

```python
# 取消は「受付」であり反映は非同期。反映前に closeOrder を投げると
# 「総有効注文数量との合計が総建玉数量を超過」して ERR-423 になり得る。
_ORDERED_SIZE_POLL_MAX_ATTEMPTS = 5
_ORDERED_SIZE_POLL_INTERVAL_SECONDS = 1.0


def _fetch_positions_after_cancel_reflection(
    client, symbol: str, *, cancelled_in_step2: bool
) -> list[dict]:
    positions = _fetch_open_positions(client, symbol)
    # Step2 で1件も取り消していないなら待つ対象が無い（通常時に遅延を足さない）
    if not cancelled_in_step2 or not positions:
        return positions

    for attempt in range(1, _ORDERED_SIZE_POLL_MAX_ATTEMPTS + 1):
        pending = [p for p in positions if _is_nonzero_size(p.get("orderedSize"))]
        if not pending:
            return positions
        if attempt == _ORDERED_SIZE_POLL_MAX_ATTEMPTS:
            break
        time.sleep(_ORDERED_SIZE_POLL_INTERVAL_SECONDS)
        positions = _fetch_open_positions(client, symbol)

    # タイムアウトしても例外にはしない。満額 close を試み、失敗は次回起動に委ねる
    return positions
```

設計上のポイントは 4 つです。

**判定は `orderedSize` で行う**。`activeOrders` の件数ではなく建玉側の注文中数量を見ます。前述のとおり、反映ラグの影響を受けにくかったのがこちらだからです。

**取り消していないなら待たない**。Step2 が 1 件も取り消していない場合、待つ対象がありません。それでも `orderedSize` が非 0 なら取消対象外の注文が原因なので、待っても解消しません。通常時に無駄な遅延を足さないための分岐です。

**タイムアウトしても例外にしない**。5 回待っても 0 にならなければ警告を出したうえで満額の `closeOrder` を試みます。ここで例外にして手仕舞い自体を止めると、決済 OCO を消した直後の建玉が損切・利確なしのまま次回起動まで残ります。決済が ERR-423 で失敗した場合も、失敗として記録し次回起動に委ねます(fail-closed)。

**間隔は 1 秒**。GET の呼出上限は 1 秒間に 6 回なので、1 秒間隔なら余裕があります(2026年8月時点)。

### 上限 5 回の根拠は弱いと明示しておく

正直に書くと、**最大 5 回(実質 4 秒)という上限に強い根拠はありません**。実測サンプルはスパイク 1 件のみで、しかも「4 秒待てば反映された」ではなく「かなり時間が経ってから確認したら反映済みだった」という粗い観測です。真の反映時間は 100ms かもしれません。

そこで、ポーリング回数と待機秒数を構造化ログに残しています(反映した場合／タイムアウトした場合の両方)。実運用で分布を測ってから上限を調整する前提の暫定値です。

### 決済の再送ゲートでも同じ指標を使う

`closeOrder` は、GMO が明示的に拒否した業務エラーの場合だけ再送します。その再送判定でも `orderedSize` を見て、**非 0 のあいだは再送しません**(二重受付を避けるため)。こちらのポーリングが短くて済むのは、本命の反映待ちが Step3 の直前で済んでいるからです。

## まとめ

- `cancelOrders` / `closeOrder` の成功は「受付」。公式のレスポンス説明も「取消受付に成功した」であり、反映済みを意味しません
- 取消 POST の直後に `activeOrders` を GET すると取消前の状態が返り得ます。件数の即時判定は反映ラグをそのまま誤判定として拾います
- 建玉の `orderedSize`(注文中数量)は、取消の反映で `"0"` に落ちるのを実測できました。反映待ちの指標にはこちらを使っています
- ERR-423 の後半条件「総有効注文数量との合計が総建玉数量よりも大きい場合」は、決済 OCO を残したまま満額決済するケースに当たります。キャンセル・ファーストという順序の根拠の一端がここにあります
- ERR-423 は自分では未観測です。公式の条件・実測した反映ラグ・予防としての実装を分けて扱い、断定はしていません
- 待機上限のような数値は、根拠の強さも一緒に記録しておくと後から調整できます。今回はポーリング回数と待機秒数をログに残しました

決済シーケンス全体(冪等性・fail-closed・決済後の残存判別)は [Kill Switch の冪等設計](https://zenn.dev/ozapon/articles/gmo-fx-kill-switch-idempotency)、POST 間隔を含むレート制御は [レートリミット設計](https://zenn.dev/ozapon/articles/gmo-fx-rate-limiter) に書いています。同じ「HTTP 200 + ボディ `status`」を参照系で踏んだ話は [約定が0件に化けた記事](https://zenn.dev/ozapon/articles/gmo-fx-http200-empty-executions)、発注ボディの数量型は [ERR-5105 の記事](https://zenn.dev/ozapon/articles/gmo-fx-err5105-ifo-size) にあります。
